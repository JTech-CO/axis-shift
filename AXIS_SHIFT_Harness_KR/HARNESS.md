# HARNESS.md — AXIS//SHIFT 마스터 운영 매뉴얼

> 기술·디자인 백서는 무엇을 만들지 정의한다. 이 문서는 그것을 어떤 순서와 증거로 구현하고, 어디서 멈추며, 어떻게 복구할지를 정의한다.

## 0. 문서 권한과 단일 진실 공급원

플랫폼 지시를 제외한 저장소 내부 권한 순서는 다음과 같다.

```text
AGENTS.md
→ HARNESS.md
→ INVARIANTS.md
→ 채택 상태 ADR
→ 현재 phase 파일
→ 기술·디자인 및 보조 docs
→ 구현 코드와 주석
```

- 현재 작업 상태: `PROGRESS.md`
- 현재 phase의 완료 기준: `phases/Mnn_*.md`
- 절대 위반 불가 규칙: `INVARIANTS.md`
- 구조·규칙 변경 이유: `decisions/`
- 제품 명세: `docs/TECHNICAL_WHITEPAPER.md`, `docs/DESIGN_WHITEPAPER.md`
- 코드가 문서와 다르면 코드를 정답으로 간주하지 않는다. 테스트와 문서를 확인하고 불일치를 명시적으로 해결한다.

## 1. 세션 루프

### 1.1 시작

1. `PROGRESS.md`에서 현재 phase와 마지막 상태를 확인한다.
2. 현재 phase의 DoR 체크박스를 검토한다.
3. 참조된 불변식, ADR, 백서 절을 읽는다.
4. 최근 증거와 실패를 재현한다. 이미 실패 중인 게이트를 건너뛰지 않는다.
5. 이번 세션의 단일 작업 묶음과 예상 검증을 정한다.

### 1.2 작업

- 한 번에 한 phase만 활성화한다.
- 변경을 작은 수직 단위로 나눈다: 실패 테스트 → 최소 구현 → 리팩터링 → 관련 게이트.
- 수학·생성기·저장·시간 로직은 UI에 연결하기 전에 순수 함수 수준에서 굳힌다.
- UI 작업은 명세된 모든 상태를 fixture로 재현한 뒤 실제 feature에 연결한다.
- 외부 API·자산·의존성 추가는 작업 편의가 아니라 제품 필요성과 오프라인 계약으로 판단한다.
- scope 밖 이슈는 `PROGRESS.md` 백로그에 남기고 현재 변경에 섞지 않는다.

### 1.3 검증

검증은 가장 작은 범위에서 시작해 아래 순서로 확장한다.

```text
관련 단위 테스트
→ 관련 패키지/feature 테스트
→ phase 전용 스크립트
→ npm run verify
→ E2E·접근성·배포 smoke
```

- 동일 명령이 같은 입력에서 같은 판정을 내야 한다.
- 수동 검증만 가능한 항목은 환경, 단계, 기대 결과, 실제 결과, 화면 캡처 경로를 남긴다.
- 자동화 가능한 수동 검증은 다음 반복 전에 테스트로 승격한다.

### 1.4 종료

1. phase 파일의 DoD와 증거를 갱신한다.
2. `PROGRESS.md`에 완료, 미완료, 다음 한두 작업, 미결, 최근 게이트를 기록한다.
3. Codex 협업 기록을 추가한다.
4. 새 결정이 있으면 ADR을 작성하고 관련 문서 링크를 갱신한다.
5. 커밋·푸시·PR은 사용자 지시에 따라 수행한다.

## 2. Phase 의존성과 병렬 작업

기본 순서는 M00 → M01 → … → M11이다. 선행 phase가 완료되지 않으면 후행 phase의 DoR를 충족할 수 없다.

병렬 작업은 다음을 모두 만족할 때만 가능하다.

- 두 작업이 동일 파일·동일 공개 계약·동일 불변식을 수정하지 않는다.
- 각 작업의 선행 DoR가 이미 충족됐다.
- 통합 게이트와 병합 순서가 사전에 정해졌다.
- 사용자가 병렬 진행을 명시적으로 허용했다.

병렬화가 일정 단축보다 통합 위험을 키우면 순차 진행한다.

## 3. 완료 판정

### 3.1 DoR

phase 진입 전 필수 조건이다. 하나라도 미충족이면 상태는 `진입 대기` 또는 `막힘`이다.

### 3.2 DoD

phase 종료에 필요한 측정 가능한 게이트다. 전부 통과해야 `완료`다.

- “화면이 보인다”, “에러가 없다”, “대충 맞다”는 DoD가 아니다.
- 핵심 기능은 결과를 직접 검증한다.
- 정합성이 필요한 두 구현은 동일 fixture를 사용해 패리티를 검사한다.
- 불변식 참조가 있는 DoD는 해당 INV가 0건 위반이어야 한다.

### 3.3 증거 수준

| 수준 | 허용 증거 | 사용 위치 |
|---|---|---|
| E0 | 주장만 있음 | 완료 근거로 불가 |
| E1 | 수동 관찰·스크린샷 | 시각 품질·실기기 확인 |
| E2 | 재현 가능한 명령과 통과 출력 | 일반 DoD |
| E3 | 자동 테스트·대량 감사·수치 리포트 | 수학·생성기·저장·성능 |
| E4 | CI와 실제 배포 URL에서 재검증 | M10·M11 릴리스 |

핵심 정확성 phase(M02, M03, M04)는 E3 이상, 최종 릴리스는 E4가 필요하다.

## 4. 검증 우선순위

1. **불변식과 규칙 정확성**: PULSE, 랭크, 분해, 결정성.
2. **핵심 기능 실효**: 실제 플레이로 목표를 해결하고 결과가 정확한가.
3. **통합 정합성**: 코어·UI·저장·공유가 같은 데이터를 해석하는가.
4. **접근성·UX**: 360px, 키보드, 색 외 표식, 모션 감소.
5. **성능·오프라인·배포**: 번들, PWA, base path, 실제 링크.
6. **제출 표현**: 썸네일, 200자 소개, 영상, Codex 기록.

상위 게이트가 실패하면 하위 단계의 성공은 릴리스 근거가 아니다.

## 5. 변경 통제

다음 변경은 코드 수정 전에 ADR이 필요하다.

- 공개 PULSE 규칙 또는 등급 규칙 변경
- 최소 펄스 수 계산법 변경
- 보드 표현 또는 최대 크기 변경
- generator seed 형식·버전·fallback 정책 변경
- 저장 스키마의 비호환 변경
- Hash Router·정적 PWA·백엔드 없음 원칙 변경
- import 경계 변경
- 공유 결과에 포함되는 정보 변경
- 원격 분석·외부 API·광고·계정 도입
- 라이선스 정책 또는 외부 자산 공급 방식 변경

ADR은 맥락, 결정, 근거, 트레이드오프, 검토한 대안을 기록한다. 기존 결정을 대체하면 이전 ADR을 삭제하지 않고 `폐기(ADR-XXXX로 대체)`로 표시한다.

## 6. 결함 심각도와 릴리스 차단

| 등급 | 정의 | 예시 | 릴리스 |
|---|---|---|---|
| P0 | 규칙·데이터·배포가 근본적으로 깨짐 | par 오답, Daily 불일치, 공개 링크 접속 불가 | 즉시 차단 |
| P1 | 핵심 흐름 또는 주요 사용자군이 완료 불가 | 모바일 PULSE 가림, 저장 복구 실패, 키보드 경로 단절 | 차단 |
| P2 | 우회 가능한 기능·표현 결함 | 특정 공유 API 폴백 오류, 비핵심 레이아웃 깨짐 | 원칙상 수정, 명시 승인 시만 유예 |
| P3 | 미세한 시각·문구 개선 | 1px 정렬, 비핵심 카피 | 백로그 가능 |

활성 P0·P1은 0건이어야 M11을 통과한다. 불변식 위반은 심각도와 무관하게 즉시 차단한다.

## 7. STOP 절차

### 7.1 STOP 조건

- 같은 실패를 서로 다른 방법으로 3회 시도해도 미해결.
- DoD를 통과하려면 테스트·임계치·범위를 약화해야 함.
- 활성 불변식을 깨야 함.
- 아키텍처·규칙·스키마·generator version 변경 필요.
- 외부 접근권한, 비밀키, 약관·라이선스 확인이 필요.
- 실기기나 실제 배포 환경 없이는 결론을 낼 수 없음.
- 일정상 필수 범위 충족이 불가능해 보임.

### 7.2 기록

`PROGRESS.md`에 다음을 남긴다.

```text
증상
최소 재현 단계
기대 결과 / 실제 결과
시도 1·2·3과 각각의 출력
현재 가설
영향받는 INV·DoD
선택 가능한 다음 결정
```

### 7.3 행동

- 임시 우회로 불변식을 깨지 않는다.
- 사용자에게 결정이 필요한 선택지를 영향과 함께 보고한다.
- 결정 전까지 독립적으로 안전한 문서화·테스트 보강만 수행한다.

## 9. 문서 갱신 규칙

- `PROGRESS.md`: 매 세션.
- phase 파일: 해당 phase 작업 때.
- ADR: 결정 즉시.
- `RUNBOOK.md`: 동일 장애 2회 이상 또는 재발 가능성이 높은 장애.
- 백서: 공개 계약·제품 범위가 바뀔 때.
- 추적표: 요구사항·테스트·phase 경로가 바뀔 때.
- QA·릴리스 문서: M10·M11에서 실제 결과로 채운다.

문서와 구현을 한 PR/작업 묶음에서 함께 갱신하여 표류 기간을 만들지 않는다.
